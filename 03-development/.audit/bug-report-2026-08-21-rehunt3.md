  `ORDER BY started_at DESC, id DESC LIMIT 1` 顯式挑 latest)。

## 3. 確認 bugs (open, 不擋 Gate 3)

### auth#1 (medium) — production auth 讀 test stub 的 `__name__`
- 位置:`taskq_api.service.auth:48-60`、`92-99`
- 問題:`_is_wrong_key_stub_active()` 透過
  `key_repo.get_active_by_hash.__name__ == "_stub_active"` 切分支;
  production 行為被 test double 的識別子綁定。
- 不擋門原因:`NOT_FOUND` 與 `None` 在 deps.py:87 都映射到 401,無
  權限提升路徑,僅「test 結構進 production 決策」的 code smell。

### auth#2 (medium, NEW) — `has_scope` 把未知 required scope 當 rank 0
- 位置:`taskq_api.service.auth:37` + `:114-123`
- 問題:`_SCOPE_RANK.get(required, 0)`;寫入端(API/CLI)目前沒人用未
  註冊 scope,所以 latent — 但未來若有人新增 `require_api_key_with_scope(
  "superadmin")` 卻忘記登錄 rank,任何 read+ key 都會 silent 通過。
- 證據:HEAD 對 `has_scope('write', 'superadmin')` 直接 probe → `True`。
- 不擋門原因:目前沒有任何 route 餵未註冊 required scope;屬於 defense-
  in-depth 缺失,非可利用漏洞。

### ratelimit#1 (medium) — T-02 緩解方案 fail-open
- 位置:`taskq_api.api.deps:51-56` + `:149-153`
- 問題:`_enforce_rate_limit` 在 `ratelimit.check` 拋任何 exception 時
  默默 admit,且位置在 `_resolve_or_raise` 之後,unauthenticated 401
  風暴完全 bypass bucket。
- 證據:HEAD 對 `ratelimit.check` monkey-patch raise RuntimeError →
  `_enforce_rate_limit` 仍 admit(fail-open)。
- 不擋門原因:屬覆蓋率缺失,token bucket 本身正確(authenticated caller
  受保護)。

### tasks#1 (low) — `list_tasks` 接 negative limit
- 位置:`taskq_api.api.tasks:108-115`
- 問題:只檢查上界 `> 200`,負值會傳到 `task_repo.list_paginated`,
  SQLite 對 `LIMIT -4` 視為「無上限」。
- 不擋門原因:需要 negative 輸入 + SQLite 特定行為;N+1 已擋。
